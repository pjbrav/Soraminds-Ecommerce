You are building a complete, working, end-to-end prototype for a technical assignment from

1. `Menu_Ingestion_Engineering_Spec.md` — the engineering specification (pipeline stages,

2. `SpiceHub_Kitchen_Menu_Upload_Template.xlsx` — the owner-facing upload template

The distilled requirements below are extracted from those files so nothing is lost if the

---

## 1. MISSION

A restaurant owner (non-technical) uploads a menu spreadsheet (.xlsx or .csv) and a folder
of menu photos (individual files or one .zip). The system automatically ingests, normalizes,
validates, and repairs the data, then produces a validated, structured, kiosk-ready menu.
Every error, ambiguity, missing field, or conflict must be resolvable BY THE OWNER through
the dashboard — zero involvement from any engineer or internal staff. Once all blocking
issues are resolved, the system publishes the final kiosk-ready JSON.

Example restaurant: SpiceHub Kitchen (Troy, MI) — South Indian / Indo-Chinese, 10 categories,
~90 live menu items. The template ships with 27 of their real items.

## 2. THE PIPELINE (follow the spec's 8 steps exactly)

```
Upload -> Column Mapping -> Field Validation -> Auto-Repair ->
Structured Output (+ RAG index) -> Owner Validation Report ->
Live Preview -> Publish
```

Owner-resolution scenarios that MUST work end-to-end:
- Missing price -> owner enters or confirms the price (inline edit)
- Ambiguous category -> owner selects the correct category (e.g., "Currys" -> Veg Curries
  or Non Veg Curries, with the suggestion surfaced)
- Unmatched image -> owner selects which menu item the photo belongs to
- Missing description -> auto-generated by LLM, flagged auto_generated: true, owner can edit
- Conflicting spreadsheet/photo information (e.g., price on a photographed menu board differs
  from the spreadsheet) -> owner resolves the conflict, choosing which source is right
- Invalid or incomplete data -> system explains the issue in plain language and guides the
  owner toward the fix

Two correction paths, neither requiring a full re-upload: (a) inline single-row edit that
re-validates just that row, (b) partial re-upload merged by item_id.

## 3. COLUMN SCHEMA (from the template's Menu Items sheet)

| Column | Required | Rules |
|---|---|---|
| item_id | No | Auto-generated MENU-0001 style if blank |
| category | YES | Dropdown, one of the 10 SpiceHub categories (tenant-configurable list) |
| subcategory | No | Free text, display grouping only |
| item_name | YES | 1-60 chars, no HTML/script tags |
| description | No | <= 200 chars; LLM-auto-generated if blank, flagged |
| price | YES | Number > 0, <= 2 decimals, < $500 sanity ceiling, no currency symbol |
| dietary_type | YES | Dropdown: Veg / Non-Veg / Egg / Vegan |
| spice_level | No | Dropdown: None / Mild / Medium / Hot / Extra Hot (default None) |
| calorie_range | No | Regex ^\d{2,4}-\d{2,4}$ (e.g., 350-500) |
| allergens | No | Comma-separated, each validated against a known allergen list |
| image_filename | YES | Must match an uploaded photo, case-insensitive |
| is_featured | No | Yes/No, default No; drives the kiosk Featured Items strip |
| is_available | No | Yes/No, default Yes |
| sort_order | No | Integer; sequential by row order within category if blank |
| tags | No | Comma-separated; feeds search and the embedding index |

NOT columns, on purpose: popularity rank, like-percentage, review count, "Most Ordered" —
these are runtime_stats populated by the Analytics block AFTER launch. The JSON schema
keeps a structurally separate runtime_stats block that is null at ingestion time.

SpiceHub's 10 categories: Veg Appetizers, Non Veg Appetizers, Veg Curries, Non Veg Curries,
Rice, Hyderabadi Dum Biryani, Breads, Desserts, Drinks, Soups. The category list (and the
allergen list) must be tenant-configurable config values, NOT hardcoded constants — a
different cuisine needs its own category set.

## 4. VALIDATION RULES (implement as a rule TABLE / config, not per-field hardcoded logic)

Collect EVERY error per row — never stop at the first one.

| Field | Rule | On failure |
|---|---|---|
| item_name | Non-empty, 1-60 chars, no HTML/script tags | Hard error |
| category | Exact match to tenant's category list, or >= 0.85 fuzzy match | Hard error |
| price | Number, > 0, <= 2 decimals, < $500 | Hard error |
| dietary_type | One of Veg / Non-Veg / Egg / Vegan | Hard error |
| image_filename | Matches an uploaded file (case-insensitive) | Hard error |
| description | <= 200 chars if present | Auto-fix if blank |
| spice_level | One of the fixed list if present | Auto-fix if blank |
| calorie_range | Regex ^\d{2,4}-\d{2,4}$ if present | Soft error |
| allergens | Each comma-separated value in known list | Soft error |
| sort_order | Integer if present | Auto-fix if blank |
| is_featured | Warn if more than ~10 items flagged featured | Warning only |
| item_name + category | Near-duplicate detection | Warning only |

Auto-repair pass (runs BEFORE anything reaches the owner):
- Trim whitespace on all text fields; strip currency symbols/commas from price ("$13.99" -> 13.99)
- Normalize dropdown casing ("non-veg" -> "Non-Veg")
- Blank description -> LLM-generate from item_name + category + dietary_type + tags; set auto_generated: true
- Blank sort_order -> sequential by row order within category
- Blank spice_level / is_available / is_featured -> defaults None / Yes / No
- Header not exact-matching -> embedding fuzzy-match >= 0.85 auto-maps; below threshold flags unmapped_column
  (only matters for non-template CSV uploads; the shipped template's headers are exact)

Blocking semantics: Publish is blocked until zero hard errors remain. Warnings never block.

Each validated row becomes one canonical record (this JSON — not the Excel — is the source

  "description": "Chicken cooked with spices and tomatoes, layered in basmati rice and exotic spices and served with boiled egg.",
  "description_auto_generated": false,

  "currency": "USD",
  "dietary_type": "Non-Veg",
  "spice_level": "Medium",
  "calorie_range": "550-700",

  "is_featured": true,

  "voice": {"audio_url": null, "status": "not_generated"},
  "runtime_stats": {

    "popularity_rank": null,

Publish semantics: version every publish (menu-v1, menu-v2, ... — never overwrite), atomic
switch of the active menu version with rollback available. Publishing triggers downstream
jobs: (1) TTS generation for new/changed items (STUB this — mark voice.status and log the
job; no real TTS required), (2) image resize/compression (do this for real with Pillow),
(3) search/embedding index refresh.

## 6. API CONTRACT (FastAPI, this exact shape)

| Endpoint | Purpose |
|---|---|
| POST /tenants/{id}/menu/upload | Accept file(s), run Steps 1-5, return uploadId |
| GET /tenants/{id}/menu/uploads/{uploadId}/validation-report | Per-row status from Step 6 |
| PATCH /tenants/{id}/menu/uploads/{uploadId}/items/{rowId} | Inline single-row fix (re-validates that row) |
| POST /tenants/{id}/menu/uploads/{uploadId}/preview | Trigger live preview (Step 7) |
| POST /tenants/{id}/menu/uploads/{uploadId}/publish | Publish (Step 8) |
| GET /tenants/{id}/menu/active | Current live structured menu |
| GET /tenants/{id}/menu/featured | Featured strip — filters is_featured: true from active menu |

Upload endpoint requirements: reject non-.xlsx/.csv by MIME type AND magic bytes BEFORE any
parser opens it; enforce max 5 MB file size and max 500 rows; store the raw upload under a
storage root keyed by tenant and uploadId (local filesystem standing in for
s3://sora-tenant-uploads/...). Malware-scan: implement a stub layer with a clear interface
and a comment naming what would run in production (e.g., ClamAV), so the pipeline stage
exists.

## 7. IMAGE HANDLING AND CONFLICT DETECTION

- Owners upload photos as individual files or one .zip; image_filename in the sheet must
  match an uploaded photo (case-insensitive). Unmatched photos (no row references them)
  and unmatched rows (no photo exists) are both owner-resolvable issues.
- If an OpenAI API key is configured, run a vision-model pass (gpt-4o or gpt-4o-mini) over
  each photo to extract any readable text (item name, price) and compare against the
  spreadsheet row. On conflict (e.g., spreadsheet says 13.99, photo shows 11.99), raise a
  conflict issue the owner resolves by picking the correct value.
- If no API key is set, degrade gracefully: skip the vision pass, note it in the report,
  and let the owner proceed — the prototype must be fully runnable without any API key.

## 8. LLM USAGE (cost-aware, graceful degradation)

- Description auto-generation: OpenAI-compatible chat model (gpt-4o-mini class) via the
  OPENAI_API_KEY env var. NEVER hardcode a key. Log token usage per call to a usage table
  (provider, model, input tokens, output tokens) — an accounting pattern worth showing off.
- Embedding fuzzy-match for column mapping and category matching: use a local
  sentence-transformers model (all-MiniLM-L6-v2) with cosine similarity — no API cost,
  deterministic, and exactly matches the spec's ">= 0.85 similarity" requirement.
- Per-item embeddings for the RAG-ready index: same local model; store vectors per item
  (JSON or .npy in SQLite is fine — no vector database needed at this scale) with the
  embedding block in the JSON record (model, vector_id, source_text).

## 9. DASHBOARD (owner-facing)

Build a single web dashboard (server-rendered HTML from FastAPI + Jinja2 + light vanilla
JS + Tailwind via CDN is enough; a DoorDash-like menu-card look, not a polished product):

1. Upload page — pick/enter tenant (default spicehub-kitchen-troy), upload spreadsheet +
   photos (.zip supported), start processing with a live status indicator.
2. Validation report — per-row table: status badge (Valid / Warning / Error), the exact
   field(s) at fault, plain-language reason + suggested fix ("Category 'Currys' not
   recognized — did you mean 'Veg Curries' or 'Non Veg Curries'?"). Inline edit controls
   per row (dropdowns for category/dietary, number input for price, text for description)
   that save via the PATCH endpoint and re-validate ONLY that row, updating its badge
   instantly. Unmatched-photo resolution: a gallery of orphan photos with item dropdowns.
3. Live preview — kiosk menu screens rendered from the same structured JSON that will be
   published: category sections, a Featured Items strip at the top driven by is_featured,
   item cards with photo, name, description, price, dietary badge. Only reachable when
   zero hard errors remain. DoorDash-style visual hierarchy (horizontal category nav,
   card grid) is the target look.
4. Publish — one click, atomic, shows the new version number, links to the active-menu
   JSON endpoint output.
5. Menu version history — list of versions with rollback.

The dashboard is the product's face: it must demonstrate the complete zero-engineer loop
convincingly, but pixel-perfection is explicitly NOT the evaluation criterion.

## 11. ARCHITECTURE AND TECH STACK (prescribed)

- Python 3.11+. FastAPI + Uvicorn. SQLite (one file) for menu_items, uploads,
  validation issues, versions, audit log, usage. Local filesystem standing in for S3
  (./storage/tenants/{tenantId}/...) with a thin storage interface so swapping in real
  object storage later is a one-class change — document this.
- Pydantic models for every API boundary. openpyxl/pandas for spreadsheet parsing.
  Pillow for image processing. sentence-transformers for embeddings.
- Validation rules, category list, and allergen list in YAML config (tenant-scoped) —
  rule table, not hardcoded per-field logic.
- Audit log: every upload, auto-repair action, owner edit, publish — who/what/when.
- pytest suite covering: every validation rule (one test per rule, plus a worst-case
  500-row file where every row has an error — the spec's load test), the auto-repair
  transformations, the re-validate-after-edit path, and the publish blocking rule.
- Type hints and docstrings throughout. No secrets in code or the repo — .env.example
  with OPENAI_API_KEY= and a README note.

## 12. BUILD ORDER (the spec's 16-item checklist, adapted to the prototype)

1. Tenant config: category list + allergen list as YAML, tenant-scoped.
2. Template generator script (produces the .xlsx with data-validation dropdowns from
   the tenant's Category Reference) — the provided template serves as the reference output.
3. Upload endpoint: MIME + magic-byte check, malware-scan stub, 5 MB / 500-row limits,
   raw storage, returns uploadId.
4. Column mapping: exact match first, embedding fuzzy-match fallback at 0.85,
   unmapped_column flagging below threshold; persist mapping for audit.
5. Field validator as a rule table; collect all errors per row.
6. Auto-repair pass (section 4).
7. LLM description generation service + auto_generated flagging + usage accounting.
8. Structured JSON writer + versioned menu documents + runtime_stats placeholder.
9. Embedding generation + tenant-scoped vector storage.
10. Validation-report API + dashboard page with suggested-fix text.
11. Inline single-row edit + re-validate endpoint + dashboard wiring.
12. Partial re-upload merge by item_id.
13. Live-preview renderer with the Featured Items strip (DoorDash look).
14. Publish: atomic version switch + downstream job triggers (TTS stub, real image
    resize/compression, index refresh).
15. Audit log across all mutating actions.
16. Worst-case load test: 500 rows, every row erroneous — must complete fast and report
    all errors.
